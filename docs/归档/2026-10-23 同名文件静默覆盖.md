# 2026-10-23 同名文件静默覆盖（P0#2e）

## 事故

给 o叔 的 322 个作品批量 `bili get --audio-only`，模板 `{uploader}/{title}.{ext}`
把视频标题里的歌名抽出来当文件名。但歌名会重复：

```
水星记 ×4    原神 ×6      唯一 ×2（告五人 / 王力宏）
暗香 ×2      知足 ×2      花海 ×2
海阔天空 ×2   打上花火 ×2   Call of Silence ×2
```

**319 首只落地 280 首，丢了 39 首**，`failed: 0`，没有任何警告。

## 根因

落盘前完全不检查目标路径：

```ts
await rename(tmpOut, target)   // target 已存在就直接覆盖
```

`rename` 在 POSIX 和 Windows 上都是"已存在则替换"。后下的歌把先下的覆盖掉了，
而任务本身是成功的（文件确实写出来了），所以 `failed` 是 0。

**这是最坏的一类 bug**：数据没了，但所有信号都显示成功。调用方只能靠
"下载前后数文件数"自己发现。

## 修法

落盘前先问"这个路径现在是什么状态"，按清单给的优先级消歧：

| 优先级 | 形式 | 什么时候用 |
|-|-|-|
| 1 | `绿色DJ（纯享版）.mp3` | 分 P 名 —— 往往就是版本说明 |
| 2 | `绿色DJ（BV1GEn26uEDT）.mp3` | 最稳，但丑 |
| 3 | `绿色DJ（2）.mp3` | 兜底 |

**同一个 bvid 重下不算冲突**，覆盖自己是预期行为（`--force` 重下就是干这个的）。

核心逻辑抽成纯函数 `resolveTargetPath(wanted, info, page, probe)`，
`probe` 是"这个路径现在是什么"的探针。这样可以单测所有分支，
不用真下 300 首去撞 —— 而且撞坏了就是丢数据。

## 怎么判断"这个文件属于哪个视频"

三档：

1. **文件名里的 `（BVxxx）`** —— 消歧时我们自己写进去的，最可靠
2. **标签里的 `SOURCE_ID`** —— 我们一直有写，是 ASCII 明文，
   在 ID3v4 的 TXXX 帧体和 Vorbis 条目里都能直接搜到：
   ```ts
   buf.toString('latin1').match(/SOURCE_ID[\x00=](BV[0-9A-Za-z]{10})/)
   ```
3. **都读不出 → 当作"别人的"**

第 3 条是保守选择，值得说清楚理由：读不出归属时覆盖一个陌生文件，
比多留一个带后缀的文件糟糕得多。前者丢数据，后者只是丑。

## 实测

**同 bvid 重下**（应该覆盖自己，不产生副本）：

```
第1次: 绿色DJ.mp3  renamedFrom: null
第2次: 绿色DJ.mp3  renamedFrom: null
目录: 绿色DJ.mp3                ← 只有一个，正确
```

**不同 bvid 同名**（造一个 SOURCE_ID 被改成别的 bvid 的文件）：

```
新文件: 绿色DJ（绿色）.mp3
renamedFrom: 绿色DJ.mp3
warnings: [ '1 个文件因重名加了后缀（见 renamed），没有覆盖已有文件' ]
目录: 绿色DJ.mp3  +  绿色DJ（绿色）.mp3    ← 两个都在
```

## 测试

8 条，覆盖三个优先级的每一级、同 bvid 不算冲突、扩展名切分。
两个方向验过能变红：

| 撤掉什么 | 变红的测试 |
|-|-|
| 退回"直接覆盖" | 6 条 |
| 把"同 bvid"也当冲突 | 1 条 |

第二条很重要 —— 不加这条测试的话，把 `same` 也当冲突会让人重下时
产生一堆 `（BVxxx）` 副本，看着像修好了，实际是另一种脏。

## 没做的

- **不处理"文件名里的非法字符导致不同歌名渲染成同一个"**。
  比如两首歌标题里都有 `/`，净化后可能撞车。这种情况现在也会触发消歧，
  结果是对的，只是名字不好看。
- **没有可选开关**（比如 `--overwrite`）。清单没要求，
  而且"默认不覆盖"本来就该是唯一行为。
