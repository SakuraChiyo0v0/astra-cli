1. 把 mihomo 从 ASF 的网络里抽出来，建成独立的 `proxy-net`

## 踩过的坑

**以为代理是 ASF 的一部分，实测它只是借用了 ASF 的网络。**
mihomo 有自己的 compose 项目，但 `networks: asf_default: external: true` —— 网络是 ASF 创建的。
后果：ASF 项目一旦 down 或重建网络，所有依赖代理的容器一起断。而且这个依赖藏在 external 声明里，不明显。
→ 新建 `proxy-net`（`--label purpose=outbound-proxy`），mihomo 和 hermes 都接进去。
`asf_default` 暂时保留在 mihomo 上做过渡，确认稳定后可以删。

**以为 Steam 愿望单需要 Web API key，实测不需要。**
`IWishlistService/GetWishlist` 只要有公开愿望单就能读。我一开始用两个示例账号测都返回 `{"response":{}}`，
误判成"需要 key"——其实是那两个账号的愿望单不公开。
用用户真实账号（76561199038682501）一测就有 111 个条目。

**私密愿望单不报错，返回空对象。** 这是 Steam 的"成功码 + 空数据"形态，
必须区分"真的没有愿望单"和"账号不公开"，否则用户会以为自己愿望单被清空了。

**以为 `appdetails` 能一次查多个 appid，实测多 appid 返回 400。**
`appdetails?appids=4000,287980` → `400 Bad Request`；单独查 `appids=4000` → 200。
→ 改成逐个请求，并发 4 条。
（这一点和很多文档说的"支持批量"不一致，实测为准。）

**`https.request({createConnection: () => secureTlsSocket})` 会二次握手。**
在已经完成 TLS 握手的 socket 上交给它，Steam 返回 400。
→ 改成直接在隧道 socket 上写 HTTP 请求头。顺便自己解 chunked 和 gzip。

**服务器会无视 `Accept-Encoding: identity` 照样 gzip。**
Steam 的 429 响应就是压缩的，不解开会拿到乱码，错误信息变得莫名其妙。
→ 代理实现里按 `content-encoding` 兜底解 gzip / deflate / br。

**库存接口对共享代理 IP 限流很严，稳定 429。**
愿望单和商店详情都正常，只有 `/inventory/...` 返回 429（响应体是 `null`）。
不是代码问题：换个出口 IP 大概率就好。已在错误里给明确提示并标 `retryable`。

## 没做

- 库存的限流重试策略（等多久、要不要换节点）—— 取决于用户的代理配置
- 商店搜索、评测、成就 —— 那些更适合自己去商店看
- SOCKS5 代理（只支持 HTTP CONNECT）
