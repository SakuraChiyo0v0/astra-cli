# 挂载盘标签不刷新：一次「以为在修 Windows，其实在修文件大小」

2026-10-22。用户报：Hermes 在 NAS 上重新打过标签，Windows 资源管理器属性里还是旧标题。

## 结论

`buildId3` / `retagFlac` 的 padding 是固定长度（MP3 1024、FLAC 4096），
改标题后**文件总大小不变**；而 Kura 的 rclone 挂载判断"远程文件变没变"**只比大小**，
于是挂载盘上永远读到旧内容。

## 我以为是 A，实测是 B

| 我以为 | 实测 |
|-|-|
| Windows 资源管理器缓存了属性 | 不是。缓存目录里的文件本身就是旧的 |
| rclone 会在 poll 时发现 mtime 变了 | mtime 变了也没用，判据里没有 mtime |
| etag 能帮上忙 | 不能。`lsjson --hash` 对 `vendor=other` 和 `vendor=rclone` 都拿不到哈希 |
| 文件被改名，旧缓存条目是孤儿 | 这只是表象。真正的问题是同名文件的内容没换 |
| 「写新文件再删旧文件」能治本 | 不成立。大小由内容决定，先删后写改不了大小 |

## 关键实测（都在沙盒目录做，没碰音乐库）

1. 原地覆盖成**同样大小**的新内容，mtime 变新 → 挂载盘读到的还是旧的
2. 改成**差 1 个字节** → 立刻重新下载，读到新内容
3. 删掉 `vfs/` + `vfsMeta/` 里的条目 → 立刻重下
4. `vfsMeta` 里的 `"Fingerprint": "6444693"` 就是字节数，没有别的判据

WebDAV 的 `getetag` 其实带了完整信息（`"18e0c152d1a835ed3742cd"`，
前缀是 mtime 纳秒、后缀是十进制大小），但 rclone 的 WebDAV 后端不用它。

## 为什么日常必中

改标签最常发生的场景就是**等字节长度**的改名：`年轮` → `花海`，都是 6 字节 UTF-8。
标题长度一样，padding 也固定，文件大小必然完全一致。

## 修法

padding 由标签内容的 sha256 决定，落在 `[512, 1535]`：

```
size = 512 + (sha256(body).readUInt16BE(0) % 1024)
```

- 同一份标签算出同一个值 → `retag` 重跑不会反复改文件（有测试守着）
- 不同标签几乎必然算出不同值 → 总大小跟着变 → 挂载盘重下
- 下限取 512 而不是维持 1024：让"旧文件（固定 1024）→ 新规则"这一步也大概率改变大小

## 第一版测试写错了，撤掉修复照样绿

第一版是拿**长短不同的标题**去比：

```ts
const shortTitle = retagMp3(original, { ...tags, title: '年轮' })   // 6 字节
const longTitle  = retagMp3(original, tags)                        // 11 字节
assert.notEqual(shortTitle.length, longTitle.length)
```

长度本来就差 5 字节，padding 写死也撞不上 —— 这个用例从来没在测 bug。

**撤掉修复、测试仍然通过**，才发现。改成两个等字节长度的标题（`年轮` / `花海`）后，
撤掉修复 MP3 和 FLAC 两条都变红，才算真的抓到了。

教训：写"必须变化"的断言时，先问自己**不修的话它会不会失败**，光跑一遍变绿说明不了什么。

## 顺带确认的两件事

- `embeddedIdentity` 只读前 64KB。B 站音频封面实测 148KB，会把 `TIT2` 挤到 64KB 之外，
  此时返回 `null`。调用方 `identityMismatch` 把 `null` 当"不知道"放行 —— 行为是对的
  （这道关是拦"明显是另一首"，不是"不能证明就拒"），但原代码没写清楚，已补注释。
- astra 写的标签**没有 `TSSE` 帧**。NAS 上那批文件带 `TSSE: Lavf62.3.100`，
  说明是 ffmpeg 写的，不是 `writeTags` —— 判断"谁改的"时这条可以用来区分。

## 后续可选

`--vfs-cache-max-age` 当前是 `87600h`（十年，等于永不），这是挂载设置里手改过的值。
不是这次问题的原因，但意味着缓存只在容量超限时才淘汰。要更早发现远程变化，
可以考虑在 Kura 挂载页加一个「清空缓存」按钮。
