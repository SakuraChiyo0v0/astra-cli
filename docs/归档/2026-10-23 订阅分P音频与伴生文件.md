# 2026-10-23 订阅分 P / 音频模式 / 伴生文件

清单 v0.12.14 后的三条。两条 P0 是同一个根因的两面，第三条是新功能。

## 1. P0#1：订阅漏分 P，而且是"永远补不上"

### 现象

订阅 `season:1060544882/1049571` 发现新视频 `BV1GEn26uEDT`（P1「绿色」+ P2「纯享版」），
任务成功、`failed: 0`，但只落了 P1，而且 astra 自己已经给了 warning：

```json
"warnings": ["这个视频有 2 个分 P，这次只下第 1 个；要别的用 --page 指定"]
```

**warning 被忽略了** —— 因为调用方（cron / Hermes）看的是 `failed: 0`。

### 两层根因

**表层的**：`collectionToItems()` 写死 `pageIndex: 0`：

```ts
meta: { bvid: v.bvid, pageIndex: 0, quality, singlePage: true }
```

**更根本的**：基线只记 bvid。

```ts
export function pickFresh(current, lastSeen, force) {
  return { fresh: current.filter((v) => !lastSeen.includes(v.bvid)) }
}
```

`BV1GEn26uEDT` 已经在 `lastSeen` 里了。所以**即使把默认值改成"下全部"，
它的 P2 也永远不会被补上** —— 这个视频不会再被当成"新的"。

用户指出这一点的原话：「只改默认值，它的 P2 永远不会补」。

### 修法

基线从 `bvid[]` 升到 `{ bvid: [已下的 P 号] }`，存在新列 `seen_pages`。

`planPages()` 三种情况：

| 情况 | 行为 |
|-|-|
| 新视频（bvid 不在基线） | 按 `pagesMode` 下全部或只 P1 |
| 老视频但多了新 P | **只下没下过的那些** ← 补 P2 的路径 |
| 老视频、P 齐全 | 跳过 |

老数据（`seen_pages` 里没有这个 bvid）按"已经下过全部"处理，
避免升级时给所有存量视频重下一遍；要核对存量用 `--rescan-pages`。

### 回写时机：只有真落盘才算下过

一开始我想在 `runBiliSubscription` 里直接记，但那里任务刚创建、还没跑。
也不能记"待下"清单 —— 失败了就永远补不上，正是原 bug 的同类错误。

最后挂在 `core/jobs.ts` 新增的 `afterFinish` 钩子上，
从 `job_items` 里只取 `status in ('downloaded', 'skipped')` 的项回写。

失败项不记，下次检查会重试。

## 2. P0#2：音频落盘位置

原来 `--audio-only` 落 `bili.dir` + `bili.template`，
想进音乐库得"先临时改 bili.dir、下完再手工搬"—— 那个流程存在的唯一原因就是这条限制。

现在两条路（`bili get --audio-only` 与订阅音频模式）都默认落音乐库。
`--to bili` 保留为显式出口。

落盘变量映射（B 站没有"歌手 / 专辑"概念）：

| 音乐模板变量 | 取什么 | 与写入标签的对应 |
|-|-|-|
| `{artist}` / `{primary_artist}` | UP 主 | `TPE1` |
| `{album}` | 视频标题 | `TALB` |
| `{title}` | 单 P 用视频标题、多 P 用分 P 名 | `TIT2` |

这样目录结构和标签说的是同一件事，播放器里不会出现"文件夹叫 A、标签写 B"。

## 3. P2#3：伴生文件

`.Metadata.nfo` / `.jpg` / `.Danmaku.ass`，配置 `bili.sidecar`（默认空）。

### 命名是扩展名追加，不是替换

```
a.mp4  →  a.mp4.Metadata.nfo      ✅
a.mp4  →  a.Metadata.nfo          ❌ 播放器认不出是同一条
```

播放器靠"文件名完全一致、只有后缀不同"来配对。写成替换扩展名的话，
Jellyfin 里就是一堆没有视频的孤立 nfo。这条踩过一次（写的第一版是替换），
后来靠测试钉住了。

### 一个顺手修的 bug

nfo 标题原本是 `${info.title} - ${page.part}`，但 B 站单 P 视频的分 P 名
经常就是视频标题本身，于是得到「绿色 - 绿色」。加了相同性判断。

这个是测试抓到的 —— 我造夹具时把 P1 的 part 设成和 title 一样，
正是线上的真实形状。

  也能刮，本地 `.jpg` 已经够用

## 追加：0.12.16 修 `--rescan-pages` 补不回存量（P0#1b）

0.12.15 上线后，Hermes 按验收命令跑，`newCount: 0`、`"没有新视频"`。

### 我当时的判断错在哪

0.12.15 里我以为"基线记到分 P"已经做到了。实际上**有两个洞**，单独看都不致命，
合起来正好卡死存量视频。

**洞一**：`run` 决定"给谁查分 P"时写的是：

```ts
else if (sub.seenPages[v.bvid] !== undefined) needPages.add(v.bvid)
```

只查"已经有 seenPages 记录"的视频。而 `--rescan-pages` 干的正是**清空记录** ——
清空之后全部变成 `undefined`，于是一个 bvid 都不查。

**洞二**：`planPages` 里

```ts
const treatAsAllDone = !isNewVideo && already === undefined && options.rescanPages !== true
```

把"记录缺失"当成"已下全部"。

两个洞连起来：`--rescan-pages` 清空 → run 不查 pages → planPages 拿到空 pages → 跳过。

### 真实数据确认

从 NAS 拷了 `astra.db` 下来看：

```
订阅 b0e020c5 | 201 个 bvid | pagesMode: all | seen_pages 有 201 条
BV1GEn26uEDT 的记录: []          ← 空数组
seen_pages 里空数组的条目数: 201 / 201
```

**201 条全是空数组** —— 因为这些视频是在引入 `seen_pages` 之前下的，
记录初始化时写了 `[]`，而旧代码把空的当成"已完成"。

### 改成 A 方案

差集严格按「视频 × 分 P」算，没有特殊路径：

```ts
const done = new Set(seenPages[item.bvid] ?? [])
for (const page of wantedPages) {
  if (done.has(page.page)) continue
  tasks.push(...)
}
```

记录缺失 = 一页都没下过。这是唯一说得通的定义 —— 空数组不可能表示"下过了"。

`run` 也改成对合集里**每个** bvid 都查分 P。代价是 201 个视频各一次 view 请求
（几秒钟），换掉的是"漏内容且永远补不上"。

`--rescan-pages` 现在只是"清空记录"的辅助命令 —— 下次 run 自然全部重算，
语义干净了。

### 验证

用 NAS 的真实数据库 + 真实 API 跑：

```
BV1GEn26uEDT 实际分 P: P1 绿色 / P2 纯享版
待下任务: [ 'BV1GEn26uEDT P1', 'BV1GEn26uEDT P2' ]
```

把实现退回旧语义（记录缺失 = 已下全部），**5 条测试同时变红**，
包括那条照着用户操作序列写的复现。

### 反思

0.12.15 我加了两条测试，都验"分 P 求差对不对"，**但用的是手造的 `seenPages`**，
从来没验"从真实基线状态出发会怎样"。

手造数据时我下意识给了 `{ BV1x: [1] }` 这种"有记录"的形状，
正好绕开了 bug 所在的分支。**用真实数据验一遍，比再写十条单测都有用** ——
这次是从 NAS 拷 db 下来才看见"201 条全是空数组"的。
