# 2026-10-21 UP 主投稿接口：试了什么、为什么放弃、怎么绕

## 目标

`astra bili space <UP>` —— 列出某个 UP 主的视频，支持批量下载与订阅。

## 真正的全量投稿接口：做不了

目标接口是 `/x/space/wbi/arc/search`（B 站个人空间"投稿"页的数据源）。

逐个姿势实测，全部失败：

| 姿势 | 结果 |
|-|-|
| wbi 签名 + 基础 UA/Referer | `-352 风控校验失败` |
| 加 `origin` / `accept` / 空间页 Referer | `-412 request was banned` |
| 加设备指纹 `buvid3`+`buvid4`（从 `finger/spi` 拿）+ `dm_img_*` 参数 | `-412 request was banned` |
| 冷却 45 秒后用最小参数 | `-352` |
| 最小参数 + `platform=web` | 直接返回风控 HTML 页 |
| 移动端 `app.bilibili.com/x/v2/space/archive/cursor` | `-400`（需 appkey 签名） |

**规律**：参数越"像浏览器"，封得越狠（352 → 412）。说明它校验的东西我们模拟不出来，
可能是登录态里的某些字段，或者需要真实的浏览器行为轨迹。继续硬啃只会让 IP 被标记。

**没有继续啃。** 这类接口的正确态度是换路，不是加参数。

## 换的路：列合集与系列（免签名，可用）

`/x/polymer/web-space/seasons_series_list?mid=<mid>` **不需要签名**，实测稳定。

对「老番茄」（mid 546195）实测返回：

```
6 个合集：合集·多人实况(23) 合集·创意解说(18) 合集·蜘蛛侠！(5) ...
11 个系列：青春旅行团(13) 蜘蛛侠！(5) 恐怖密室(7) ...
```

**为什么这条路够用**：UP 主的视频绝大多数本来就按合集/系列组织（尤其是连载、系列企划）。
"列合集 → 逐个下"覆盖了大部分真实的批量需求。真正散装的单条视频只能靠 `bili search` 或手给链接。

## 过程中补的两个小坑

**系列名不在列表接口里。**
`series/archives` 只返回 `aids / page / archives`，没有名字。名字要单独查
`/x/series/series?mid=&series_id=`。补上后标题从「系列 4684427」变成「青春旅行团」。

**合集 meta 里的 `name` 是合集名，不是 UP 名。**
一开始误把它当 UP 名，结果 `name` 显示成「合集·多人实况」。
UP 名要查 `/x/web-interface/card?mid=`（免签名可用）。

## 现在能做什么

```sh
astra bili space mid:546195              # 列出该 UP 的合集与系列
astra bili collection series:546195/4684427   # 列某个系列的视频
astra bili bulk series:546195/4684427         # 下载整个系列
```

实测全链路通：space 找到 13 个视频的系列 → collection 列出 → bulk 建任务。

## 仍然做不了

- **某个 UP 的全部投稿**（不分合集的那种）
- 订阅 UP 主（同上，底层接口不通）

如果将来一定要做，唯一稳的路是让用户提供一个**真实登录的 B 站 cookie**（SESSDATA），
用那个会话去调。但这会让 CLI 依赖更易变的东西，也有账号风险，暂时不做。
