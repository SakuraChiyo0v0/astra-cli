# 2026-10-23 歌词文件改名与状态词统一

## 1. 逐字歌词写成了永远不会被读的文件名

### 现象

逐字歌词（增强 LRC，`<mm:ss.xx>`）一直存成 `.word.lrc`。
`music have --refresh` 认它、`retag` 认它，但**播放器和 Navidrome 不认** ——
它们只按 `<歌名>.lrc` 找 sidecar。逐字歌词写了几个月，从来没被任何客户端读过。

### 改成什么

```
<歌名>.lrc       逐字（增强 LRC）
<歌名>.line.lrc  逐行（纯文本）
```

增强 LRC 是普通 LRC 的超集（每行仍是 `[mm:ss.xx]` 开头，额外带 `<mm:ss.xx>` 逐字标签），
所以认普通 LRC 的播放器也能读 `.lrc`。逐行那份留给不认逐字标签的客户端兜底。

### 迁移兼容

- `.word.lrc` 仍识别（存量文件的旧名），`maintain.ts` 和 `retag.ts` 三种扩展名都认
- `retag` 搬文件时 `.lrc` / `.line.lrc` / `.word.lrc` 一起跟着走
- 返回值新增 `lineLyricFile`，旧的 `wordLyricFile` 保留（指向同一份），不打断已有脚本

### 踩过的坑：`lyricText()` 只剥方括号

生成 `.line.lrc` 用的是 `lyricText()`，它原本只做 `line.replace(/\[[^\]]*\]/g, '')`。
从增强 LRC 转过来时，`<00:12.34>` 这些逐字标签**原样留在文本里**，
不认逐字标签的播放器会把它们当正文显示。

这个 bug 是新写的测试抓到的 —— 一开始我写了个「自己写文件、自己读文件」的假测试，
它当然通过。改成测真实的 `lyricText()` 输出后立刻变红：

```
AssertionError: 逐行版没有 <mm:ss>
```

修法：再叠一个 `.replace(/<[^>]*>/g, '')`。

## 2. 任务项状态词跨域不一致

### 现象

```
music job --items  → status: done / skipped
music get          → data.status: downloaded / already_have
```

调用方按 `status == "downloaded"` 过滤任务项，**静默拿到空集合**，
把 101 项全判成"异常"。

### 改成什么

任务项统一用 `downloaded`。带一条 DB 迁移把历史 `done` 改写成 `downloaded`。

**只改 `job_items.status`，不动 `jobs.done` 那个计数列** ——
那是列名不是状态值，改列名会破坏已有查询。

### 验证

迁移实测（建库 → 降到第 25 条迁移 → 插旧数据 → 重开触发迁移）：

```
迁移前: [{"seq":1,"status":"done"},{"seq":2,"status":"skipped"},{"seq":3,"status":"failed"}]
迁移后: [{"seq":1,"status":"downloaded"},{"seq":2,"status":"skipped"},{"seq":3,"status":"failed"}]
```

`skipped` / `failed` 原样保留，只有 `done` 被改写。

运行时也验了一遍（注册假 handler 跑真 worker）：

```
downloaded 项: ['downloaded','downloaded'] | job.done = 2
skipped 项:    ['skipped']                | done = 0  skipped = 1
```

## 3. VR 2FA 提示（复核：已修复）

清单说"提示文案似乎还没替换干净"。核对结果：**用户可见的提示已经是对的**：

```ts
next: `... 然后 \`astra vr login --code <验证码>\`。5 分钟内有效`
```

源码里还剩两处 `login 2fa <code>`，都不是用户可见的：
- `src/vr/auth.ts:108` 的**注释**，解释"原先那样写是错的"
- `docs/归档/...md` 里的历史记录

如果机器人仍显示旧文案，要确认它跑的是不是最新产物。

## 踩过的坑

**写测试时"自己造数据自己读"等于没测。**
第一版歌词命名测试是 `writeFileSync(base + '.lrc', enhanced)` 然后 `readFileSync` 断言它有
`<mm:ss>` —— 这只证明了 fs 能读写。真正该测的是**生成这份内容的那段代码**，
换成调 `lyricText()` 之后立刻抓到了尖括号残留。

**改枚举之前先数清楚有多少地方在用。** `ItemStatus` 的 `done` 散在：
类型定义、`ItemOutcome`、`qualitySummary`（音乐和 B 站各一份）、`updateJobCounts` 的 SQL、
两个 handler 的返回值。漏一个就 typo 到运行时才炸。

## 没做

- 存量 `.word.lrc` 没有改名。要迁的话用 `astra music retag`（它认三种命名），
  或者手工 `mv`。NAS 上当前是 0 个 `.word.lrc` / 111 个 `.line.lrc`，说明部署侧
  已经手工迁过一轮了。
- `jobs.status` 的 `done`（任务级，不是项级）没改。它是另一层语义（整个任务完成），
  和项级的 `downloaded` 不冲突。
