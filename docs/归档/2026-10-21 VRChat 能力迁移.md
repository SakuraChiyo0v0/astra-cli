# 2026-10-21 VRChat 能力迁移

从 astrahub 迁移 VRChat 到 astra-cli。astrahub 那边是 3158 行、63 个操作、15 个模块。

## 做了什么

按 astra-cli 的域结构重写，不是照搬：

```
src/vr/api.ts       传输层（固定官方源、强制 UA、错误归一）
src/vr/auth.ts      账号密码登录 + 两步验证 + 会话
src/vr/data.ts      只读：好友 / 世界 / 实例 / 通知 / 收藏 / 群组 / 头像 / 余额
src/vr/actions.ts   写操作：加删好友、收藏、邀请、改状态、通知已读
src/vr/commands.ts  命令层
src/core/confirm.ts 通用的写操作二次确认（音乐域红心也改用它）
```

19 个命令。只读命令直接返回；写命令统一"预览 → 令牌 → 确认"。

## 踩过的坑

**以为 `/health` 是免认证的探活端点，实测返回 401。**
`GET /api/1/health` 带 UA 时返回 401 `{"error":{"status_code":401}}`。换成 `/config`：
免认证可用，但返回几十 KB（整个客户端配置）。所以探活时只读 `availableLanguageCodes` 判断可达，
不把整份配置带进对话。

**不带 User-Agent 会被 Cloudflare 拦成 403，而不是 401。**
实测：`curl` 不带 UA → 403；带上 UA → 401（需要认证）。403 看起来像"没权限"，
实际是"没告诉服务器你是谁"。这条沿用自 astrahub 的记录，这次亲自验证了。

**登录是 GET 不是 POST，而且要 Basic 认证。**
`GET /auth/user` + `Authorization: Basic base64(urlencode(user):urlencode(pass))`。
密码里有 `@`、`:` 时不做 URL 编码会 401 —— 这条要求很反直觉。

**两步验证的会话要用第一步的 cookie。**
开启 2FA 时第一步只返回中间会话，`requiresTwoFactorAuth` 告诉你可用方式。
`POST /auth/twofactorauth/<方式>/verify` 成功后**不会**下发新会话 cookie，
verify 的响应只是票据；真正能用的还是第一步那个 `auth=<uuid>`。

**写操作的确认机制值得抽出来。**
音乐域的红心写过一套"预览 + 一次性令牌"，VRChat 有 7 个写操作，再复制一遍就是重复代码。
抽成 `core/confirm.ts`：按用途分文件存待办（`pending-<purpose>.json`），
令牌绑定"动作 + 参数指纹"，参数顺序不影响指纹。

## 范围说明

astrahub 的 63 个操作里，这次搬了 19 个命令覆盖的核心部分。没搬的：

- 经济交易明细（`vrchat.economy.transactions`）：只做了余额
- 群组的加入/退出/公告/权限（写操作，且用得少）
- 头像的创建/选择/搜索：只做了"我的头像"和"当前头像"
- 收藏分组的创建/删除
- 权限与系统统计类

这些都是"平时用不上"，真要用了再按同样的结构补。

## 补记：分组、头像、系统（同日）

补了三块。

**收藏分组**：`POST /favorite/groups` 建、`DELETE /favorite/groups/{name}` 删。
建之前先查同名分组（省得建出两个重名的），删之前把分组里的收藏数报出来 —— 删分组会连带删掉那些收藏。

**头像**：`PUT /avatars/{id}/select` 切当前、`PUT /avatars/{id}/selectFallback` 设回退。
切换前先去"我的头像"列表核对这个 id 是不是自己的，不是的话在预览里明确标出来 —— 上游会拒，
但提前说清楚比让用户等一个失败好。

**系统与权限**实测：
- `/visits` 免认证，直接返回一个数字（当时是 50378）
- `/time` 免认证，**这次返回标准 ISO 格式** `2026-10-21T10:23:31+00:00`；
  astrahub 在 2026-09-23 记录的是 `09/23/2026 20:35:32` —— 上游改过格式。
  所以这里只原样返回字符串，不解析、不换算时区
- `/permissions` **需要登录**，返回的是"VRChat 定义了哪些权限"，不是"我这个账号有哪些权限"。
  命令说明里写清楚了，免得 AI 把它当成后者转述

至此 VRChat 域 27 个命令。价格、经济交易明细、群组的加入退出与权限管理仍未搬。

## 补记二：经济类（同日）

补了余额、交易明细、收藏上限。

**余额端点原来用错了。** 我第一版写的是 `/user/subscription`（想当然），
astrahub 用的是 `GET /user/{id}/balance`。后者需要先拿到自己的 id 再拼路径。
两处都做完了才发现，已改。教训：同一平台的接口别凭印象写，先看参考实现。

**余额缺失是 null 不是 0。** 0 表示"余额真的是零"，null 表示"上游没给这个字段"。
两者含义不同，混起来会把"没数据"说成"你没钱"。

**交易明细的 status 有新值时原样转述。** 已知 active / failed / succeeded / cancelled，
但上游随时可能加。所以不写死枚举、不把未知值解释成成功或失败，原样带出去。
原始响应也整体保留在 `raw` 里，字段随版本变化时不用改代码。

**收藏上限三类分开给。** `/auth/user/favoritelimits` 返回 avatar / friend / world 三个数，
不合并成一个总数 —— 合并了就看不出是哪类满了。

## 补记三：统一任务视图（P0-2）

加了 `astra jobs` / `astra job <id>`，不用记域名就能看所有域的任务。

**发现一个隐藏的真 bug**：`jobs.quality` 列是 `NOT NULL`，但没有"档位"概念的任务
（VRChat 类）建不出来 —— 测试里 `profile` 不传就报 `NOT NULL constraint failed`。
这解释了为什么之前一直没暴露：音乐传音质、B站传画质，两条路都恰好有值。

**差点做错的地方**：我一开始以为要重建表、把 `domain` 加成独立列。
查真实数据库才发现 `jobs` 表根本没有 `domain` 列 —— domain 是存在 `meta` JSON 里的
（`{"domain":"bili"}`），由 `toView` 读出来、缺省当 music。按那个思路写迁移会直接失败。

**SQLite 改约束只能重建表**，所以迁移是「建新表 → 拷数据 → 删旧表 → 改名」。
真实数据库（15 条记录、4 个任务、23 个任务项）先复制副本验证、再正式执行：
版本 17→22，数据一条不少，`quality` 已可空，无档位的任务能插入。
正式执行前留了 `astra.db.pre-migrate` 备份。

## 补记四：凭据统一与磁盘用量（P0-3 / P0-4）

**凭据统一**：`core/sessions.ts` 原本只覆盖网易云和 B 站，**漏了 VRChat**（后来加的域没同步）。
补齐后 `astra login` 列三域。另加 `astra login clear [域]`：只删本地文件、不调上游登出 ——
存在的理由是"会话文件坏了（空文件 / 权限 644 / 格式坏），正常 logout 都进不去"时还能收拾干净。
各域自己的 `logout` 仍然是首选（它知道各自的端点和语义）。

**磁盘用量**：`core/disk.ts`，走一遍目录树累加 + `statfs` 拿文件系统剩余。
两个设计点：
- **有上限**（默认 20000 个文件）：目录特别大时 doctor 不能跑几分钟，超了就标 `truncated` 而不是静默少算
- **阈值告警**：剩余低于 10GB 标 `lowSpace`。按一张无损专辑约 0.5GB 估，10GB 还能装二十张

在 NAS 上实测：音乐 501MB / 34 文件，视频 277GB / 240 文件，磁盘剩 2.5TB（70%）。
视频目录那 277GB 是 B 站合集下出来的，符合预期。

## 补记五：备份与审计（P1-1 / P1-2）

**备份**：`astra backup`。数据库用 `VACUUM INTO` 而不是复制文件 ——
`astra.db` 是 WAL 模式，直接拷可能拿到不含最新事务的旧数据。会话文件拷过去后强制 600。

一个边界：**从没下载过东西时库里根本没有 `astra.db`**（表是第一次写数据才建的），
这时只备份到会话是正常的。第一版没在返回值里说明，容易误以为备份完整，后来加了 `hasDatabase` 标记。

`restore` 是危险操作，做了两层保护：有任务在跑直接拒；覆盖前把当前库改名留 `.replaced-<时间戳>`。
NAS 上实测：14 首歌、4 个任务的库备份出来 73KB，读回去完整。

**审计**：`core/audit.ts`，写操作走 `audited()` 包装，成功失败都记，失败仍原样抛出（审计不能挡住主流程）。

**踩到一个不好发现的 bug**：detail 原本 `JSON.stringify(...).slice(0, 2000)` ——
按字符截断 JSON 会切成半个字符串，读的时候解析失败，**整条记录都读不出来**。
改成：能放下就原样存，放不下就换成 `{truncated:true, keys:[...]}` 的说明，绝不存半截。

这个 bug 我第一版的测试没测到（因为后来给读取端加了容错，坏 JSON 变成 `{unreadable:true}` 不崩了）。
补了一条直击要害的断言（`detail.unreadable` 必须为 undefined），再把旧实现注回去确认测试会红。

## 补记六：全盘检修（v0.10.5）

系统过了一遍：类型 → 测试 → 构建 → 产物一致性 → 真实部署 → 各域功能 → Hermes 集成。

**产物与部署一致**：本地 `dist/astra.mjs` 与 NAS 上那份 sha256 完全相同，没有"改了没同步"的情况。

**抓到两个真问题**：

1. **`astra audit` 的选项全是假的**。usage 里写了 `--domain / --failed / --since / --limit`，
   但 `options` 一个都没声明，照着用法敲直接报 `Unknown option '--limit'`。
   这类"文档与实现对不上"只在运行时暴露，所以补了一个测试：扫所有命令的 usage，
   里面出现的 `--xxx` 必须在 options 里声明过。注入缺失验证过会让测试变红。

2. **NAS 上有两个 skill 的 name 撞了**。`skills/vrchat` 和 `skills/astra-vrchat` 的 frontmatter
   都写着 `name: astra-vrchat`（前者是早期部署名，0.8.4；后者是后来改的名，0.8.5）。
   Hermes 遇到重名只加载一个。删掉旧的，并顺手把 `bili` 统一成 `astra-bili`，
   现在三个 skill 的目录名与 name 完全一致。

**巡检确认健康的**：14 首音乐全部可完整解码（ffmpeg 无报错）、B 站 277GB/240 文件正常、
备份含审计表增长到 90KB、红心往返实测且审计记录完整（like → unlike 两条）、
飞书重启后 WebSocket 重新连上。

**一个不是问题但值得记的**：曲库 11 首没有逐字歌词，因为它们是逐字功能上线**之前**下的。
要用的话重下即可，不是 bug。

**那次 `find -print0` 报"文件不存在"是脚本的编码问题**，直接用完整路径验证文件是好的 ——
差点误判成数据损坏。

## 补记七：飞书链路实测 + 上下文成本（v0.10.5 之后）

**飞书链路终于有实证了**：用户在飞书里发 `/model cn:deepseek-v4-flash`，
Hermes 正常响应并弹出 Large Context Switch Warning —— 说明网关、鉴权、消息收发都是通的。
之前我一直说"没在飞书里实测过"，现在这条可以划掉了。

**顺手处理了上下文成本问题。** 那个会话已经 166,558 tokens，之后每句话都要重读这 16 万。
根因有两个：
1. Hermes 默认按"上下文窗口的 50%"触发压缩。第三方模型窗口大，16 万还没到阈值，所以一直不压
2. 换模型会让 prompt cache（按模型 key）整份失效，等于一次全价输入

处理（都加在 `deploy/hermes/config.yaml`，并在线上直接改过、`hermes config get` 确认生效）：
- `compression.threshold_tokens: 80000` —— 到 8 万就压，不等比例阈值
- `model.switch_context_confirm_tokens: 100000` —— 换模型时若上下文过大先警告。**没关掉**：
  换模型确实会让缓存全失效，这条提醒是有价值的，只是别让它频繁打扰
- `compression.idle_compact_after_seconds` 没开：Hermes 版本文档里这个键存在，但当前配置没验证过它在这个版本有效，先不冒险

**踩到一个配置位置坑**：`switch_context_confirm_tokens` 看着像个独立段，实际是从 `model:` 段里读的
（`hermes_cli/model_selection_guards.py`）。写成 `model_switch_guard:` 会被静默忽略 ——
用 `hermes config get model.switch_context_confirm_tokens` 验证过才敢确定。

## 补记八：上下文阈值不该卡死（同日修正）

上一节把 `threshold_tokens` 设成 8 万，理由是"16 万 token 每轮重读太贵"。用户反问
"好歹是 100 万窗口"，我去实测了一下缓存，**发现自己的前提就是错的**：

**WorkBuddy2API 支持 prompt cache，第 2 次起命中 99.9%。**
同一段 4422 token 的请求连打三次：

| 次数 | prompt | cache hit | cache miss |
|-|-|-|-|
| 1 | 4422 | 0 | 4422 |
| 2 | 4422 | 4416 | 6 |
| 3 | 4422 | 4416 | 6 |

所以"重读 16 万历史"根本不等于付 16 万的全价 —— 除第一次外，绝大部分命中缓存。
拿这个当压缩的理由是站不住的。

**改成 40 万**（1M 窗口的 40%）。换模型提醒的阈值也同步改成 40 万，
否则每次换模型都弹一次警告，反而变成噪音。

**真正的成本尖峰只有换模型那一下**：缓存按模型 key，换了就整份失效，那才是全价一次。
所以那条提醒留着、只是放宽阈值，是对的。

**教训**：做成本判断前先确认计费模型。我假设了"每次都全价"，实际有缓存，
这个错误假设会让配置变得过分保守、损害可用性。
