# 2026-10-23 `music retag`：把落盘规则的改动补到存量文件上

## 起因

落盘规则改过好几轮，每次都只对新下载生效：

- 合作曲归到主艺术家（`Lady Gaga, Bruno Mars` → `Lady Gaga`）
- 群星合辑归到 `合辑/`，标签写 `Various Artists`
- 新增 `{primary_artist}`

前两份归档都写了一句「存量文件不动」——不是不想动，是**没有能安全动的工具**。
已经下好的几千首还停在旧目录旧标签上，播放器里同一张专辑仍然散成好几张。

## 做了什么

`astra music retag [--keyword kw] [--dry-run] [--confirm <token>]`

按当前规则重新算每首歌的标签与落盘路径，然后搬文件、重写标签。

## 三条安全边界

这个命令会**移动和重写用户的真实文件**，失败代价是丢歌。所以宁可啰嗦：

### 1. 默认只预览，带令牌才动手

复用 `core/confirm.ts`（红心、VRChat 写操作同一套）：第一次调用只返回
「哪些要动、动到哪」+ 一次性令牌，5 分钟有效、只能用一次。

选这套而不是"加个 `--yes`"，是因为这个命令的调用方是 AI。带 `--yes` 的话，
AI 只要拼一个参数就能把用户的几千个文件搬走，而它并不知道搬完之后是不是还对。

### 2. 先算完全部目标路径，确认无冲突才动手

三类冲突，命中任意一条整批拒绝：

- **两首歌算出同一个目标路径** —— 后写的会把先写的顶掉，等于凭空少一首
- **目标位置已有不认识的同名文件** —— 会覆盖掉用户的歌
- **目标路径逃出音乐目录** —— `renderTemplate` 后的路径必须落在 `musicRoot()` 内

"改了一半"是最糟的状态：用户不知道哪些动了哪些没动，重跑又要重新判断。
所以不做部分执行。

大小写按平台判：Windows / macOS 上 `Idol` 和 `idol` 是同一个文件，
冲突检测要按这个口径比，否则真到 `rename` 才发现撞了。

### 3. 写标签保音频字节

复用 `writeTags`，写前写后比 `audioPayload` 的哈希，和下载时同一条铁律。

**歌词和封面必须显式带过去。** `writeTags` 是整块替换（FLAC 的 VORBIS_COMMENT、
MP3 的整个 ID3v2 头），不然后两者就丢了。所以加了 `tags.ts` 的 `readTags` 读回歌词，
封面用已有的 `extractCoverArt`。

## 踩过的坑

### 曲库里的 id 会过期，而网易云的 id 会被另一首歌复用

写第一版时，计划阶段直接拿 `library.native_id` 去 `songDetail` 查专辑，
查到什么就用什么算 albumartist。

测试时随手编了一个 id `999001` 当夹具，结果：

```
{"id":"999001","title":"Claquent les voiles","artists":["Anouar Brahem"],"album":"Vague"}
```

**ID 是真实存在的，属于另一首歌。** 如果曲库记录过期（改过名、手改过库、
从别的机器搬来的 `astra.db`），`retag` 会把用户的文件搬进
`Anouar Brahem/...` 这种完全不相干的歌手目录 —— 比不整理糟得多。

→ 加 `sameRecording()`：先比标题 + 第一位歌手（都做归一化），对不上就整组跳过，
并在结果里写明「库里是 X，网易云这个 id 是 Y」。
归一化口径和去重指纹用同一套（去括号附注、NFKC、小写、去标点）。

### `prepare()` 返回的字段名和预览撞车

第一版这样写：

```ts
return { data: { ...prepared, status: 'needs_confirmation' } }
```

`prepare()` 的返回值里有个 `preview` 字段（内容就是传进去的那份预览），
摊平之后把 `data.preview` 顶成了外层对象，而调用方期望的是 `data.summary` / `data.sample`。
实测输出：

```
status: needs_confirmation | summary: undefined
```

`token` 也在 `data.token` 里但被 `preview` 那层挡住了 —— 等于**预览完全看不见**。
→ 明确展开成「令牌 + 计划」两层，不靠 `...` 图省事。

### 测试自己的漏洞：只验证结果，没验证防线

「写标签不动音频」那条测试原本只断言"最终文件的音频哈希 == 原始哈希"。
但把 `retag.ts` 里的哈希校验整段删掉，**测试照样绿** —— 因为 `writeTags` 本身没坏，
不校验的话结果也是对的。

换句话说那条测试测的是 `writeTags`，不是 `retag` 的防线。

想让防线真正被测到，得制造一个"会改坏音频"的 bug。验证方式：
临时把 `retagFlac` 改成 `file.subarray(audioStart + 100)`，测试立刻变红。

这条留在这里提醒：**"结果正确"和"防线生效"是两件事**，
只测前者的话，防线烂掉了也没人知道。

### 判成问题的条目仍然声称"要移动"

身份校验那段最初是事后覆盖 `problem` 字段：

```ts
? { ...planned, problem: '...' } : planned
```

结果 `moves` 还是 `true`。执行阶段按 `!problem` 过滤，所以不会真的搬，
但**预览里会显示"要搬 1 个"而实际一个都不搬**。计划和执行的判据必须一致，
否则用户看到的数字是假的。→ 判成问题时同时清掉 `moves` / `tagsChange`。

## 验证

`npm run check` 通过（268 项测试）。retag 相关 13 项，覆盖：

- 冲突检测三种（同目标 / 目标被占 / 大小写不敏）
- 执行后音频载荷哈希不变
- 真损坏时中止（用 `retagFlac` 注入 bug 验证过会红）
- `.lrc` 跟随搬运
- 曲库路径同步更新，`music have` 不报缺失
- id 对不上时拒绝迁移

端到端手测（真网易云 id `2034742057`）：

```
预览：旧目录/旧专辑/01 旧歌.mp3 → YOASOBI/アイドル/アイドル.mp3
执行：{"status":"retagged","moved":1,"tagged":1,"failed":[]}
文件树：YOASOBI/アイドル/アイドル.mp3 + .lrc
```

令牌机制：错令牌 → `TOKEN_MISMATCH`；用第二次 → `NO_PENDING_ACTION`。

## 没做

- **不删空目录。** 搬走之后 `旧目录/旧专辑/` 会留下空壳。删目录风险高
  （判断"空"的时机、并发写入），留给用户自己清。
- **不重下。** 只改标签和路径，不动音频。音质升级是 `music upgrade` 的事。
- **不改 `{track}` / `{year}`。** 曲库里没存这两个字段，硬算会算出和下载时不同的路径。
  模板里用了这两个变量的用户，retag 后路径可能和"如果现在重下会怎样"不完全一致 ——
  但和**当前记录**是一致的，不会来回震荡。
- **不处理 `m4a` / `ogg`。** `writeTags` 本来就不支持，会如实报"暂不支持写标签"。
