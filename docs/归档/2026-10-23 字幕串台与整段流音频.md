# 2026-10-23 字幕串台（P0#10）与整段流音频

Hermes 需求清单第四版新增的 P0#10：`bili subtitle` 返回**别的视频**的字幕，
同一个 BV 每次调用结果还不一样。批量跑 205 个视频，145 个"有字幕"里 89 个时长对不上。

## 1. 根因：用错了接口

原代码走 `https://api.bilibili.com/x/player/v2?bvid=&cid=` —— **不带 wbi 签名**的那个。

拿真实登录态连调 6 次，同一个 `BV19K421a7kx` + `cid=1486028738`：

```
0 [('zh-CN', '//aisubtitle.hdslb.com/bfs/subtitle/28c81e445'), ('ai-zh', '.../prod/1')]
1 [('zh-CN', '//aisubtitle.hdslb.com/bfs/subtitle/28c81e445'), ('ai-zh', '.../prod/1')]
2 [('zh-CN', '//aisubtitle.hdslb.com/bfs/subtitle/28c81e445'), ('ai-zh', '.../prod/1')]
3 [('zh-CN', ''),                                               ('ai-zh', '')]          ← 整批空
4 [('zh-CN', '//aisubtitle.hdslb.com/bfs/subtitle/28c81e445'), ('ai-zh', '.../prod/1')]
5 [('ai-zh', '.../prod/1')]                                                            ← zh-CN 丢了
```

三个症状：**URL 会空**、**条目会少**、**URL 永远是同一个值不刷新**（说明是缓存/CDN 层的旧链）。
"永远同一个值"是最要命的一条 —— 那条 CDN 路径上的内容可能已经换给别人了，
于是拿到的是**别的视频**的字幕，而不是报错。

换成 `x/player/wbi/v2`（带签名）后，4 次调用的内容哈希完全一致：

```
0 [('zh-CN', 62, 154.3, '1255208b'), ('ai-zh', 82, 153.7, '9b23d724')]
1 [('zh-CN', 62, 154.3, '1255208b'), ('ai-zh', 82, 153.7, '9b23d724')]
2 [('zh-CN', 62, 154.3, '1255208b'), ('ai-zh', 82, 153.7, '9b23d724')]
3 [('zh-CN', 62, 154.3, '1255208b'), ('ai-zh', 82, 153.7, '9b23d724')]
```

wbi 版每次给的 URL 都不同（带时效签名），但指向的内容相同。
**URL 每次都变才是正常的**，一直不变反而可疑。

### 为什么之前没发现

`fetch('')` 在 Node 里会抛错，而原代码是 `if (!response.ok) continue` ——
抛错根本走不到那行。所以 URL 空的时候是**整个进程炸掉还是静默跳过**，
取决于外层怎么兜。清单里看到的"有时没字幕、有时别人的字幕"就是这个的两种表现。

## 2. 自检：怎么判断"这是不是这个视频的字幕"

加了一条时长校验，但**第一版判据是错的**。

一开始按清单写的"末时间与时长差超过 ±10s 就报错"实现，跑第二个验收例子直接误杀：

```
BV1VE421w7Ah（年轮，4:32=273s）
→ ai-zh 字幕末时间 240.8s，相差 32s，被丢弃
```

但那条字幕的内容是 `♪ 眼圈勾勒成指纹 ♪` —— **就是《年轮》的歌词，完全正确**。
差 32s 是因为歌曲结尾有 30 多秒纯音乐尾奏，AI 字幕本来就不会覆盖。

**正确判据是只卡上限，不卡下限**：

- 末时间 **> 视频时长 + 2s** → 必然是别的视频 → 丢弃
- 末时间 **< 视频时长** → 正常（片尾黑屏 / 纯音乐 / 没人说话）

清单里"末时间应在 270s 左右"是它按 ±10s 估的，不是实测值。需求写的验收标准本身
带着同样的错误假设 —— **验收条件也要用实测去验**，不能照抄。

## 3. 顺带修的：整段流的音频

查 `bili get --audio-only` 时发现另一条路从没走过音频管道：

```ts
if (play.durl.length > 0) {
  bytes = await downloadFile(durl.url, tmpOut, signal)   // 存成 .mp3 就完事
  await rename(tmpOut, target)
}
```

`durl` 是**非 DASH 的整段流**（番剧、部分老视频），下来的是 flv/mp4，**画面和声音在同一个文件里**。
原样存成 `.mp3` 意味着：扩展名说谎、播放器按 mp3 解、没有标签、没有 BV 号。

修法和 DASH 分支一致：先下到临时文件，再走 `processBiliAudio`（ffmpeg `-vn` 会丢掉视频轨）。
两条路现在共用一个 `toAudio()` 闭包，避免以后再分叉。

## 4. 测试怎么写的（踩了"测试没打到点子上"的坑）

第一版测试是：造一个带画面的 mp4，喂给 `processBiliAudio`，断言产出 mp3 且有 BV。
**然后把 durl 分支退回原样，测试照样绿** —— 因为它验的是 `processBiliAudio`
（这个函数本来就是对的），而 bug 在 `downloadPage` **要不要调它**。

改成把分支决策抽成纯函数 `audioPlan(audioOnly)`，测试直接打它。
现在把 `audioPlan` 改回 `return 'raw'`，测试立刻红：

```
✖ 分支判定：整段流 + 只取音频，必须过音频管道
```

这个教训在 `music retag` 那次也踩过（"测试只验结果不验防线，删掉哈希校验照样绿"）。

## 5. 验证

真实调用，不只是单测：

```bash
# 幂等：5 次输出一致
for i in 1 2 3 4 5; do ASTRA_HOME=/tmp/subtest/home node dist/astra.mjs \
  bili subtitle BV19K421a7kx --out /tmp/idem$i; done
md5sum /tmp/idem*/*.srt     # 每次都是 98291c5b… / 76dba82b…

# 验收案例 1：zh-CN 62 条、末时间 154.28s（与清单期望一致）
# 验收案例 2：年轮 4:32 → ai-zh 47 条、末时间 240.8s，正常写入不再误杀
```

两条自检防线都验过能变红：
- 退回 ±10s 双向卡 → 3 条测试红
- 去掉上限检查 → 2 条测试红

## 6. 没做的

- 清单建议的"有 zh-CN 就先用，ai-zh 单独命名，不能互相覆盖" —— 文件名本来就按 `lan` 区分
  （`-zh-CN.srt` / `-ai-zh.srt`），不存在覆盖。只加了排序：人工字幕先写
- 批量 205 个视频没重跑（那要几十分钟）。单个案例验了三次以上，判据本身也有单测兜着
