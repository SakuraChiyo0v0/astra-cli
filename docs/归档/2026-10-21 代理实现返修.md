# 2026-10-21 代理实现返修（v0.12.1）

## 做了什么

1. 代理层从"只能发 GET"改成"任意方法 + body"，并把重试、错误归一挪到统一路径上
2. 修入口判定在含空格路径下静默失效
3. 补 `steam-credentials.json` 的 gitignore、脱敏真实 SteamID64
4. 补测试：代理传输 12 项、入口判定 6 项
5. 补齐 Steam 与代理的文档（README / skills / deploy / PLAN）

## 起因：一次代码通读

v0.12.0 交付时 `npm run check` 全绿、真机也跑通了愿望单。但通读 `core/proxy.ts` 和
`core/http.ts` 发现三个问题，其中第一条属于"当下能用、换个配置就出事"。

### 一、经代理的请求一律变成 GET，body 丢失

`httpRequest` 里原本只把 `headers` 转给代理层，`proxiedGet` 的请求行又是硬编码的：

```ts
const lines = [
  `GET ${target.pathname}${target.search} HTTP/1.1`,   // ← 写死的
  ...
]
```

**当时为什么没炸**：投用时的配置是
`include: steampowered.com,steamcommunity.com` + `exclude: bilibili.com,music.163.com`，
写请求基本都是网易云和飞书，都被 exclude 挡住了。愿望单、商店详情、库存恰好全是 GET。

**为什么仍然是真事故**：`proxy.include` 留空的语义是**全部走代理**（不是谁都不走）。
只要有人只设 `proxy.url` 不设 `include`，网易云的登录轮询、
红心、飞书 webhook 全部变成无 body 的 GET。上游会报错，但错误信息里不会有任何
线索指向"代理"，排查方向会整个跑偏。

实测（真隧道代理 + `postman-echo.com`）：

```
修复前：调用方传的是 POST，实际拿到: 404（请求变成 GET，body 没了）
修复后：status 200，回显正文含 secret=1
```

顺带发现的同类问题：这条路径**绕过了 `retries`**。Steam 那边设了 `retries: 1`，
直连会重试、走代理不会 —— 同一个命令因为域名不同而行为不同。

### 二、代理挂了会把 `INTERNAL` 漏给调用方

```
$ ASTRA_PROXY=http://127.0.0.1:19999 astra steam wishlist --user ...
{"ok":false,"error":{"code":"INTERNAL","message":"connect ECONNREFUSED 127.0.0.1:19999",
 "hint":null,"retryable":false}}   ← exit 1
```

`maybeProxiedGet` 抛的是裸 `Error`，没经过 `toAstraError` 那一层的归一。
正确的形态是 `NETWORK_ERROR` / exitCode 5 / `retryable: true`，
而且 hint 该直接说"检查代理是否和目标容器在同一网络"。

**教训**：加一条旁路（这里是"走代理"）时，那条旁路上的错误要复用主流路径的归一逻辑，
否则就是给错误契约开了一个洞。

### 三、`proxy.include` 留空 = 全部走，这个语义没人写清楚

`config list` 原文只写了"留空 = 全部走"，但同一批配置项里 `proxy.url` 的"留空"是"不用代理"。
同一组配置里两个"留空"含义相反，中间没有任何提示。已经在 description 里补了
"留空 = 全部走代理"和"留空 = 不排除"，并在 `deploy/README.md` 里写出推荐的三条 `config set`。

## 入口判定：同一个病换了个成因

`main.ts` 里那段注释本来记着两次踩坑（产物改名、临时脚本命名），结论是"改成比对路径"。
新的实现是：

```ts
const selfPath = new URL(import.meta.url).pathname
```

**`pathname` 是百分号编码的。** 路径里有空格时它长这样：

```
pathname : /C:/Users/.../q%20a/probe.mjs
argv[1]  : C:\Users\...\q a\probe.mjs
```

永远对不上。于是"退出码 0、零输出"的静默失败原样复现。实测：

```
$ node "/tmp/ok path/astra.mjs" version
[exit=0]        ← 零输出
```

改用 `fileURLToPath(import.meta.url)`，再加 `realpathSync` 处理软链
（Node 解析模块 URL 会跟随软链，`argv[1]` 不会）。同时把 `endsWith` 的模糊比对
换成 `path.resolve` 之后的严格相等 —— `endsWith` 那种写法会让 `/a/b` 被误判成 `/x/a/b`。

## 其它

- `steam-credentials.json`（Web API key）不在 `.gitignore` 里，而**这个仓库是公开的**。
  已有的规则只覆盖 `*-session.json`，名字对不上。补了一条并加注释说明为什么不能靠通配。
- 真实 SteamID64 出现在 hint、归档、测试里，按本项目"文档/夹具要脱敏"的约定换成了假号。
- `appDetails` 的注释写"一次最多查 50 个（Steam 会截断），超出内部自动分批"——
  实际代码是逐个请求、并发 4，根本没有分批也没有上限。这类"注释与实现不符"在本项目
  已经被点过名，属于该改的一类。

## 测试怎么写才算数

两条新测试都验证过"撤掉修复会变红"：

| 测试 | 撤掉修复后的表现 |
|-|-|
| `tests/proxy-transport.test.ts` | 3 项失败（POST/PUT body、httpRequest 的 POST 通路） |
| `tests/entry.test.ts` | 4 项失败（含普通路径 —— 因为 `%20` 编码在所有路径上都存在，只是没空格时恰好不影响比对） |

入口那条特别值得记：**把 `pathname` 换成 `fileURLToPath` 之后，连"普通路径能执行"这项
都从绿变红再变绿** —— 说明它真的在测入口判定，而不是碰巧因为别的原因通过。

测试用的是**打包产物**而不是源码。踩过的坑全在"产物怎么被启动"上，测源码抓不到。

## 没做

- SOCKS5 代理（只支持 HTTP CONNECT）
- 代理的 DNS 解析（现在是本地解析目标域名再 CONNECT，走 `remote` 解析要改 CONNECT 的目标写法）
- HTTP/2 上游（经代理时只写 HTTP/1.1）
- Steam 库存的 429 重试策略 —— 取决于用户代理配置，越重试限得越久
