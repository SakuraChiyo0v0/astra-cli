# 2026-11-10 统一入库与懒加载（0.56.0）

> 工作记录。上半段是动手前定的方案，「结果」一节是做完之后的实测。

## 起点（实测，2026-11-09 线上）

两套库：

| 库 | 位置 | 存什么 |
|-|-|-|
| 状态库 | `<ASTRA_HOME>/astra.db`（SQLite，`core/db.ts` 的 `db()`，同步 API，`user_version` 41） | tracks 335 / jobs 65 / job_items 3205 / subscriptions 3 / subscription_runs 91 / audit_log 144 / schedules 5 |
| 资产库 | `db-url` 指向的 PG（`core/db/index.ts` 的 `openDatabase()`，异步 `Conn`） | assets / files / roots / events、auth、hermes.*、crawl.* |

状态库里还有一份**早期资产库残留**（assets 310 / files 310 / roots 5 / events 11 / schema_migrations 3）
—— 那是 `db-url` 配上 PG 之前、资产库还落在 SQLite 时写的。PG 里是现行的那份，这份不迁。

`db()` 调用点：11 个文件 93 处；它们导出的同步函数被 21 个文件 169 处调用。

## 方案

**状态表进 `openDatabase()` 那个库**（线上就是 PG）。表名不变（`tracks` / `jobs` / …），走迁移引擎
（`astra_0007_state_tables`），SQLite / PG 两套 DDL。

为什么不是「保留 SQLite，双写 PG」：双写正是 `mirrorFile` 那条路，结果就是现在这样两边对不上。
要一份真相就只能有一份。

为什么不按领域拆 schema（`music.tracks`）：subscriptions / jobs 本来就是各域共用表，靠 kind / meta.domain 区分；
拆了反而要改所有跨域查询（`astra jobs` 列全部域）。

### 关键决策

1. **API 变异步**。`Conn` 只有 Promise 接口，PG 驱动没有同步调用。所有 `db()` 调用方改成
   `await state()` 风格。这是这次改动量的主体。
2. **一个进程一个连接，懒打开**。`core/state.ts` 的 `state()` 第一次调用时 `openDatabase()`，
   之后复用；`main()` 的 finally 里关。worker 进程同理。
3. **迁移不自动跑的老规矩，状态表破例**：状态表是 CLI 自己运行的前提（不建表 `music get` 都跑不了），
   所以 `state()` 首次打开时检查 `astra_0007` 是否已应用，没有就执行一次（迁移引擎本身带咨询锁 / immediate 事务，并发安全）。
   资产库其它迁移仍然要 `astra db migrate` 显式跑。
4. **一次性数据搬迁**：`astra db import-state [--from <astra.db>]` 把老 SQLite 的 7 张表搬进当前库，
   幂等（按主键 upsert），搬完不删老文件，改名 `astra.db.migrated-<时间>` 留底。
   部署时手动跑一次；`doctor` 发现老库还在且新表是空的就提示。
5. **SQL 方言**：`insert or replace` → `insert … on conflict … do update`；`order by rowid` → `order by created_at`；
   PG 的 bigint 列返回字符串 → 读出时一律 `Number()`。
6. **backup**：`astra backup` 原来 VACUUM INTO 状态库。改成：当前库是 SQLite 就 VACUUM INTO；
   是 PG 就提示用 `astra db backup`（那条已经会 pg_dump），只备会话文件。

## 懒加载（P2）

最后的做法和动手前设想的不一样的地方：

- **没有生成静态命令索引**。路由只看首词：首词是领域名就 `loadDomain(首词)`，是 `db` / `lib` 就用 core 自带的，
  其它（`help` / `jobs` / `config` …）是 core 命令，一个领域都不加载。只有 `help`（不带前缀）、`doctor`、`login`、
  `auth doctor` 和 `lib adopt` 要全量
- **core 反向依赖用清单钩子拆**，而不是把领域代码挪进 core：`DomainModule` 加了 `doctor` / `sessions` / `adoptIdentity` 三个可选字段。
  漫画页认领原来靠 `comic/manifest.ts` 顶层的 `registerAdoptIdentity()` 副作用，懒加载后 `lib adopt` 根本不会 import comic，
  所以改成清单字段、`library.ts` 认领前 `loadAllDomains()` 收一遍
- **产物是「入口桩 + 版本目录」**：`dist/astra.mjs`（几行）→ `dist/releases/<版本>/astra.mjs` + `chunks/`。
  原因是目录不能原子覆盖：后台 worker 跑到一半、部署换掉一半 chunk，它下一次 `import()` 就是新旧混杂。
  现在 worker / steam 挂机钉在自己的版本目录（`core/entry.ts` 的 `pinnedEntry()`），调度走桩（`launcherEntry()`）

## 结果（实测）

### 状态并库

在 NAS 上建一个临时 PG 库 `astra_unify_e2e`，用线上 `astra.db` 的快照跑：

| 表 | 源 | 新插 | 第二次 |
|-|-|-|-|
| tracks | 335 | 335 | 0 |
| jobs | 65 | 65 | 0 |
| job_items | 3205 | 3205 | 0 |
| subscriptions | 3 | 3 | 0 |
| subscription_runs | 92 | 92 | 0 |
| audit_log | 149 | 149 | 0 |
| schedules | 5 | 5 | 0 |

`leftBehind`：assets 310 / files 310 / roots 5 / events 11 / schema_migrations 3（早期资产库残留，按设计不搬）。

之后 `jobs` / `music have` / 四个域的 `subscribe list` / `schedule list` / `audit` 读出来的数和线上一致；
`schedule disable/enable` 写审计，新 id 接在 150、151（序列推进生效）；`comic get --background` 起 worker、
任务在 PG 里从 queued 走到 done、文件落地；`lib scan --adopt` 认出 `comic:1489560_c1_p1..p4`。

### 懒加载

NAS 上同一份 `ASTRA_HOME`，各跑 5 次取最好：

| 命令 | 0.55（单文件） | 0.56 |
|-|-|-|
| `version` | 249 ms | 149 ms |
| `music have --limit 1` | 271 ms | 184 ms |
| `jobs --limit 1` | 249 ms | 165 ms |
| `lol --help` | 256 ms | 160 ms |
| `help`（全量） | 290 ms | 258 ms |

入口 85 KB；`version` 共加载约 420 KB（入口 + core + pg 驱动）。steam-user 那 6.6 MB 只有 steam 命令会碰。
对外表面（`tests/fixtures/surface.json`，help 全量 + 配置键探针）懒加载前后逐字节一致。

### 顺手修的

- `upsertAsset` 先查后插之间有竞态：后台下载 mirror 和 `lib scan --adopt` 同时跑会 `duplicate key`，整批回滚。
  插入加 `on conflict (id) do nothing`
- music skill 里「改音乐目录名」的步骤直接 `sqlite3.connect(astra.db)` 改 `tracks`，并库后那个文件不再是现行的库，
  改成 `astra db query … --write`

### 没做 / 留着

- `pg` 驱动仍在入口里静态加载（约 190 KB）：线上每条命令都要先到 PG 验令牌，懒了也省不下
- 旧的 `astra.db` 搬完改名留底，没有自动删
