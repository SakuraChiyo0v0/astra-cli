# 2026-10-21 任务体系抽取与跨 id 去重

## 做了什么

1. 把音乐的批量骨架抽成 `core/jobs.ts`，B 站复用
2. B 站批量：收藏夹、合集、单视频全部 P
3. 曲库重复判定从"只认 id"改成"标题 + 歌手 + 时长分桶"指纹

## 踩过的坑

**以为任务表可以原样复用，实测业务字段对不上。**
`jobs.quality` 存音质、`job_items.artists` 存歌手，这些是音乐的形状。B 站需要的是画质、分 P、UP 主。
没有加一堆域专用列，而是加一个 `meta` JSON 列：表结构固定，业务字段各域自己解释。
显示层把 `quality` 统一叫 `profile`（音乐是音质，B 站是画质），`artists` 叫 `subtitle`。

**以为 `getConfig` 对未知键返回默认值，实测直接抛错。**
B 站 worker 里读 `bili.concurrency`，配置项没登记 → 整个 worker 进程起不来，
任务状态变成 `interrupted`、`done 0`。这个是抽查日志才发现的，光看命令返回值只会以为"任务刚建还没跑"。
教训：新增域时配置项要和代码一起登记，`getConfig` 的严格性在这里反而帮倒忙——它让错误发生在最不容易看到的地方。

**以为指纹"取整到秒"够用，实测同一首歌会算出不同值。**
同一首《群青》来源间时长差 0.9 秒：213.2s / 212.5s / 213.9s。
四舍五入会落进 213 / 212 / 214 三个不同的值，去重直接失效。改成**按 5 秒分桶**才稳定。

**以为补指纹只要处理 null，实测旧值必须全量重算。**
第一版回填只补 `fingerprint is null`。但算法从"取整到秒"改成"5 秒分桶"后，
老记录里已有的 `群青|yoasobi|248` 是错的（新算法给 `49`），留着反而永远匹配不上。
改成 `backfillFingerprints(true)` 全量重写，并加了测试记录这个坑。

**B 站 UP 主投稿列表拿不到。**
`/x/space/wbi/arc/search` 带不带 wbi 签名都返回风控 HTML（`<!DOCTYPE html>`）。
没有硬啃，改成只支持收藏夹和合集，并在错误信息里说清楚"不支持按 UP 主页批量"。
遇到 HTML 时单独报 `BILI_RISK_CONTROL` 而不是"不是 JSON"——后者会让人误以为是代码 bug。

## 当下的事实

- 音乐批量在新任务体系下实测正常（2 首，24bit + flac）
- B 站批量实测：10 个分 P 全部下完，时长核验一致
- 跨 id 去重实测：把《群青》的 id 改掉后，用原 id 请求返回 `already_have`，并指出已有的是哪个 id

## 没做

- UP 主主页批量（风控）
- 收藏夹分页上限 50 页（防止超大收藏夹一口气拉几千条）
- B 站音频入曲库（翻唱 / live 能不能像音乐一样写标签）
