## 做了什么

`bili get --audio-only` 且 `bili.tag=true` 时，除了原有的 title / artist / album / date / 封面，
再写两个字段：

| 标签（MP3） | 标签（FLAC） | 值 |
|-|-|-|
| `TXXX:BILIBILI_BVID` | `BILIBILI_BVID` | `BV1GJ411x7h7` |
| `TXXX:BILIBILI_URL` | `BILIBILI_URL` | `https://www.bilibili.com/video/BV1GJ411x7h7` |

`music/tags.ts` 的 `TagData` 加了 `extra?: Record<string, string>`：ID3 写成 `TXXX:<键>`，
FLAC 写成同名 Vorbis 键。没有为这两个字段去焊死一个接口 —— 音乐域以后要带自己的溯源字段也能直接用。

## 踩过的坑

### 1. BV 号本来就在标签里，只是没人看得见

`SOURCE_ID` 从 B 站音频管线第一版起就写的是 bvid（0.10 就有）。所以第一反应是
"这条需求不是已经有了吗"。**但需求说的是"人能不能看到"，不是"文件里有没有"** ——
`SOURCE_ID` 是自定义键，主流播放器不显示；Navidrome 的界面上也不显示。
需求里写的场景（转码、进别的库、被播放器改名）之后，用户能查的只有播放器**显示**出来的字段。

### 2. ffprobe 对 TXXX 的键名报法不统一

新加的断言一开始写死 `read['txxx:bilibili_bvid']`，本机跑红了：

```
+ actual - expected
+ undefined
- 'BV17x411w7KC'
```

同一份文件，`-show_entries format_tags` 输出的是裸键 `BILIBILI_BVID`，
而带 `TAG:` 前缀的场景下 ffmpeg 会报成 `TXXX:BILIBILI_BVID`。这是**读法差异，不是写入失败** ——
先确认原始 ID3 帧确实写进去了（直接按帧头解析，能看到
`TXXX / \u0003BILIBILI_BVID|BV17x411w7KC`），才敢确定是断言的问题。

断言改成两种键名都认：`read.bilibili_bvid ?? read['txxx:bilibili_bvid']`。
**教训**：验证 ffprobe 读出来的标签时，别假设键名的具体形态，先打印一次实际的键集合。

### 3. 文档里 `--audio-only` 一直写成"输出 m4a"

`skills/bili/SKILL.md` 的 Quick Reference 和 `bili get --help` 都写着"输出 m4a"，
但实际从 0.10 起默认就是 `bili.audio-format=mp3`（因为只有 mp3 / flac 能写标签）。
AI 助手照着文档做，会以为下下来的会是 m4a。顺手一起改了。

## 验证

真实下载，不是只看单测：

```bash
# MP3 路线
ASTRA_HOME=/tmp/astra-e2e ASTRA_VIDEO_DIR=/tmp/astra-e2e-video \
  node dist/astra.mjs bili get BV1GJ411x7h7 --audio-only
ffprobe -show_entries format_tags .../01.mp3
#   → BILIBILI_BVID BV1GJ411x7h7 / BILIBILI_URL https://www.bilibili.com/video/BV1GJ411x7h7

# FLAC 路线 + {bvid} 模板变量
astra config set bili.audio-format flac
astra config set bili.template '{uploader}/{bvid} {title}.{ext}'
#   → .../索尼音乐中国/BV1GJ411x7h7 【官方 MV】....flac，Vorbis 键 BILIBILI_BVID / BILIBILI_URL 都在
```

两条测试都做过"撤掉修复确认变红"：去掉 `extra` 那行，`bili-audio-tag` 立刻红；
`tags` 那条的 FLAC / MP3 两侧也都断言了 BV 字段。
