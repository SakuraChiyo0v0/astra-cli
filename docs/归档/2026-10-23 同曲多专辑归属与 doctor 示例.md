# 2026-10-23 同曲多专辑归属（P4#5）与 doctor 示例（4f）

## P4#5：并行下载让"谁先下完谁占"

### 现象

给 Michael Jackson 一次下 5 张专辑，5 个 job 并行。astra 做全局去重
（同一首只存一份），但判据只看"这首歌在不在库里"：

```ts
const hit = byId ?? findByFingerprint(...)
if (hit && !hit.missing && !options.force) return existingResult(hit, quality)
```

**胜负由下载完成顺序决定，等于随机。**

实测：HIStory(1995 精选集) 抢到了 Billie Jean / Man In the Mirror，
Thriller(1982) / Bad(1987) 把这几首判成 skipped。

用户看到的是"专辑不完整"，不是"重复被去掉了" —— 这两件事在他眼里完全不同。

### 判据

清单定了四级，我照做并补了两条细节：

1. **发行年份最早** —— Thriller 1982 胜过 HIStory 1995
2. 同年时：录音室 > EP/单曲 > 未知 > 精选/合辑/现场/原声 > Remix
3. 再相同：tracknumber 靠前
4. 还分不出 → **保持现状**

第 4 条是关键。如果"分不出"时返回 `true`（认为 a 更优先），那就退化成
"传进来的第一个赢"，而传进来的顺序取决于下载完成顺序 —— 又回到原点了。

所以 `preferredAlbum(a, b)` 必须是**反对称**的：分不出时两边都返回 `false`。
有专门的测试钉这一点，还有一条"六种排列都选出同一张"。

### 未知类型放中间档

`albumTypeRank(null) === 2`（和 EP 同档），不是 1 也不是 4。

放最前会让未知压过真·原专辑，放最后会让精选集压过原专辑。中间档意味着
**遇到未知就退回看年份** —— 那是更可靠的判据。

### 让位：不只是跳过

原来的逻辑只有"跳过 / 下载"两态。现在多一态：

已有那份属于"更差的专辑"时，这一轮要把它**搬**到正确位置 ——
删旧记录与文件，重新下到本专辑目录，并记 `music.reassign`：

```
music.reassign { title: 'Billie Jean', from: 'HIStory', to: 'Thriller', fromYear: 1995, toYear: 1982 }
```

代价是重新下载一次（而不是 `rename` 搬文件）。选这样是因为：
目标路径由模板渲染，改名后标签里的 `TALB` / `TRCK` 也得跟着变 ——
搬文件还得重写标签，和重下一次的成本差不多，而重下更简单可靠。

### 存下来的元数据

判归属要年份和专辑类型。老记录里没有，所以每次都要再查专辑接口 —— 不划算。

新增 `tracks.album_id` / `tracks.album_year`，下载时存下来。下次比较直接读。

专辑类型（`录音室版` / `精选集`…）是网易云 `/api/v1/album/{id}` 一直返回的字段，
之前没解析。

## 4f：doctor 示例的占位符

```
实测：…/Bilibili/示例UP主/示例分P.mp3     ← 出现了"分P"，但音频模板没有 {part}
```

根因不是模板错了，是**示例数据选得不好**：音频模板的 `{title}` 走 `songTitleOf`，
规则是"标题里有《》取歌名，没有才退回分 P 名"。示例标题"示例视频标题"没有《》，
于是拿到了分 P 名"示例分P"。

改成 `示例视频标题《示例歌名》`，音频那条展开成 `示例歌名` —— 准确了。
顺带给视频模板两个分 P，否则单 P 时 `{part}` 是空的，看不出它进文件名。

## 没做的

- **没有跨 job 的协调**。判据是"下载时读库里现状"，两个 job 同时下同一首歌时
  仍可能都读到"库里没有"，然后都下 —— 后写的覆盖先写的（`on conflict`）。
  结果仍然正确（因为判据一致），只是多下了一次。要彻底避免得加锁，
  但那是另一个量级的复杂度，且最坏情况只是多消耗一次带宽
- **存量记录没有 album_year**，所以第一次遇到老记录时只能按"不知道"处理。
  跑一次 `music have --refresh` 不会回填这个（它补的是规格）。
  要回填得重下或单独写个迁移，目前没做

## v0.12.22 复测：归位把歌搬丢了（P4#6）

0.12.22 上线后，Hermes 实测发现**归位会真丢歌**：

```
库里已有《沈香学》（含 残機）→ 再下《2026 Special Edition》（精选集）
→ 沈香学/02 残機 被搬到新专辑目录
→ 调用方从目录看到"新专辑里有、旧专辑没了"，误以为是重复副本，删掉
→ 原文件彻底丢失（丢了 2 首，只能重下整张专辑）
```

### 我错在两处

**第一处：先删再下。**

```ts
await rm(existing.path, { force: true })   // ← 删了
forgetTrack('wy', existing.id)
existing = null
// ...然后才 resolveUrl + 下载
```

中间任何失败（网络断、磁盘满、Ctrl-C）都会让文件真的没了。
正确顺序是**先下好、确认落盘、再清理旧的**。这和"先写临时文件再 rename"是同一个道理。

**第二处：归位方向没限制。**

我当时实现的是"新专辑更优先就归位"，两个方向都开了。但反方向（把原专辑的歌搬进
精选集）会让用户已经整理好的目录凭空少歌，而他从目录层面看不出这是"归位"，
只会觉得"新专辑多了两条副本"。

### 改成什么

**只允许一个方向**：精选/合辑/现场 → 录音室原专辑。

判据要求两端信息都在：

```ts
const theirsSecondary = albumTypeRank(theirs.type) >= 4
const mineMoreOriginal = albumTypeRank(mine.type) < albumTypeRank(theirs.type)
const strictlyOlder = ...
if (!(theirsSecondary && (mineMoreOriginal || strictlyOlder))) → 不动
```

年份缺失 / 类型未知 / 同年 → 一律不动。**在不确定时搬用户整理好的文件，
代价远大于"这首歌暂时待在精选集里"。**

为此加了 `tracks.album_type` —— 只看年份不够：同年出的重混版不该把原版挤走。

### 为什么没有完全按清单第 1 条"绝不移动"

清单第 1 条说"已有文件绝不移动"，但那和 #5 的"原专辑优先"直接冲突：
要落地 #5 就得动文件。跟用户确认后取的是中间方案 ——
**只放开"精选 → 原专辑"这一个方向**，因为那个方向上原专辑本来就该有这首歌，
搬过去只会让库更正确。

## P4#7：job_started 结构

清单说 `music get` 返回 `data.job.id`、有的版本是 `data.jobId`。

查了一遍：起任务的命令其实**已经都是** `data.job.id` 了。
真正不一致的是两个订阅命令 —— `music subscribe add` 和 `bili subscribe run`
返回裸的 `jobId`。补上 `job: { id }`，旧字段保留。

help 的 conventions 也写清了怎么看、怎么等。

## v0.12.23 复测：做到真正的「文件不可变」（P4#6 最终形态）

用户看完 0.12.23 的评价是：

> 功能已经够了，现在缺的是**「文件不可变性」的约束**。
> 其它都挺好，我把 #6 放第一位 —— 它是唯一会静默丢数据的问题。

这句话点出了一个我没做到的事：0.12.23 虽然改成"先下后删"，但**仍会在
「精选 → 原专辑」这个方向删文件**。那不是不可变，只是"延迟删除"。

### 改成默认绝不移动

```ts
if (!couldReassign || options.reassign !== true) → 跳过，不碰文件
```

只有显式 `music get <专辑> --reassign` 才归位。

理由值得写下来：`tracks.file_path` 是**事实**，不是缓存。用户可能已经按这个布局
整理过目录、做过备份、写过脚本、在播放器里建过播放列表。为了"这首歌待在更正确的
专辑里"去改它，是在拿用户的数据赌一个**推测出来的偏好** —— 而且账单是静默的
（目录里凭空少一首，没有任何提示）。

代价说清楚：先下的精选集会永久占着那首歌，原专辑那次是 skipped。
想纠正就跑一次 `--reassign`，显式的、可预期的。

### 重复曲目要有解释

只记 `skipped` 不够 —— 调用方看到"专辑少了 2 首"会以为下载失败。返回里加：

```ts
duplicateOf: { album, albumId, albumYear, path, reassignable }
```

`reassignable: true` 就是在说"这首值得归位，加 `--reassign` 就能做"。

## 复测中又抓到自己两个 bug

### 1. `album_year` 存成 55399

```
残機 | 沈香学 | album_year: 55399 | album_type: 专辑
```

根因：`track.publishTime` 是**秒**（1686067200），`album.publishTime` 是**毫秒**
（1686067200000），我在两个地方都乘了 1000，还混着用：

```ts
albumYear: (track.publishTime ?? album?.publishTime)! * 1000   // ← 专辑本来就是毫秒
```

年份正是判归属的**第一判据**，错了就全错。

### 2. `albumTypeRank` 认的是想象的标签

我写了 `/录音室|studio/` → 1 档、`/精选|合辑/` → 4 档。
实测网易云：

```
沈香学(2023)                     type: "专辑"
ZUTOMAYO - 2026 Special Edition  type: "专辑"   ← 它是精选集，但 type 也是"专辑"
```

**这个字段根本不区分录音室和精选集。** 我的分档逻辑在真实数据上永远落到中间档，
`theirsSecondary` 恒为 false —— 归位一次都不会触发。

修正后：认得 `"专辑"` 归 1 档，并把**年份提为主要判据**，类型只在能区分时作补充。
现在 `2023 原专辑` 和 `2026 精选集` 同日而语时，靠年份就能判出该谁让位。
